# UC-12 — Deliver workspace failure and attention notifications

- **Actor:** System; owner configures recipients
- **Trigger:** Failed/UNKNOWN delivery, overdue schedule, capability review, connection/bridge failure, or exhausted retries
- **Preconditions:** Workspace exists; external channels optional
- **Related decisions:** ADR-004, ADR-007, ADR-013, ADR-015

## Main flow

1. Configure webhook and/or SMTP recipients per workspace, with encrypted credentials and event selection.
2. Persist a redacted event atomically with the relevant result; enqueue deduplicated notification deliveries.
3. Include workspace label/ID, publication/destination identity, safe error category, event ID, and authenticated detail link.
4. Deliver asynchronously with bounded backoff: at most three total delivery attempts. Webhooks carry a signature, timestamp, and stable event ID for receiver deduplication.
5. Record delivery success/failure and show the event in the workspace dashboard regardless of external delivery.

## Alternative flows

- No external channel: keep the in-app event; do not silently use another workspace's recipient.
- Endpoint failure: preserve delivery status and retry without blocking publishing or generating recursive notification storms.
- Default payload excludes draft text, images, prompts, tokens, raw provider bodies, and signed URLs. Text snippets require explicit workspace opt-in.
- Outbound webhook URLs reject private/link-local/metadata destinations and unsafe redirects by default. Intentional internal endpoints require a deployment-level allow-list; SMTP hosts are explicitly configured.
- A 401/403 credential problem is actionable and not automatically a retryable publishing error.
- Shared provider outages produce deduplicated/rate-limited summaries while retaining per-workspace visibility.

## Postconditions and UI

External delivery is best effort; persisted in-app events remain authoritative. A test notification names the workspace and exact recipient before sending.

- 2026-11-16 — Second slice implemented (steps 1 and 4, webhook channel only): Flyway V12 adds `notification_channel` (workspace-unique label, SSRF-validated URL, sealed HMAC secret, csv category filter, enabled flag) and the `notification_delivery` outbox (`UNIQUE(event_id, channel_id)`, PENDING/SENT/FAILED, attempts, redacted `last_detail`, `next_attempt_at`). `OutboundWebhookGuard` enforces arc42 §8: https required unless the host is on the deployment operator allow-list (`APP_NOTIFY_ALLOWED_INTERNAL_HOSTS`), userinfo denied, private/loopback/link-local/any-local/multicast/CGNAT 100.64/10 ranges denied, `localhost`, `metadata.google.internal` and 169.254.169.254 hard-denied even when allow-listed, and DNS is resolved at save time and re-resolved at send time (DNS-rebinding protection). The signing secret is generated server-side (32 random bytes, hex) and stored only sealed with the ADR-007 cipher bound to AAD `<slug>:notify-webhook:<label>` — never plaintext, never shown again. `WebhookSender` POSTs a redacted JSON payload (eventId, eventKey, workspaceId/Label, category, summary, optional publication/delivery/schedule ids, occurredAt — never draft text, tokens, media or provider bodies) with `X-SCP-Event-Id`, `X-SCP-Timestamp` and `X-SCP-Signature: t=<ts>,v1=<hex HMAC-SHA256(secret, ts + "." + body)>` (step 4); POST never follows redirects (3xx = permanent failure), 2xx = SENT, 4xx = permanent FAILED, 5xx/transport = retryable, and response bodies are never read into logs or details. `NotificationDeliveryService` enqueues one deduplicated row per enabled, category-interested channel when an event is recorded and settles due rows with bounded backoff (`base * 2^(n-1)` × jitter [0.8, 1.2), capped) and at most 3 total attempts (step 4); delivery failures never create events, so notification delivery cannot recurse (alternative flow 3). The dashboard manages channels (add / toggle / send test / delete with FK-safe outbox cleanup) and shows the newest 5 outbox rows per channel; `NotifyWorker` polls behind `APP_NOTIFY_WORKER_ENABLED` (off in tests). All lookups are workspace-scoped and fail closed on foreign ids (ADR-013). 267/267 tests green. Remaining later slices: SMTP channel, rate-limited shared-outage summaries (alternative flow 6), connection/bridge-failure events (trigger list), test-notification polish.
